## Asking the user

- Ask for wanted behavior and features first, with short examples of each
  option's observable result. Infer the mechanism and actions from the answers
  and present them for one confirmation; write or act on them only after it.
  Ask a mechanism question only where the confirmed behavior leaves several
  clean mechanisms.
- Compose rounds under the global instructions' Ask in rounds. On a large
  board, scope the round by [Priority](../shared/work-tracking.md#priority)
  first: the highest-priority unblocked question and every ready question
  sharing its premise, root cause, consumer concept or flow.
- When the user flags one instance, find all of its kind, including earlier
  rulings, and show the list before asking about scope.
- Walk through each round in chat first, readable without arc context: items
  and ids in brackets, the answered question (and the posed one if different),
  one line per decision-protocol step and every choice. Define each term, tool
  feature or earlier artifact an option relies on in one clause at first use
  (what it is, where it runs); drop arguments that do not apply to the case.
  Make contested choices questions.
- Before the walkthrough, re-screen your own rulings under decision-protocol
  Options; classify sequencing and process choices as the planning session's
  call.
- Disclose your own rulings in that walkthrough, before asking: entailed
  decisions, defect-fix behaviors, dropped or narrowed parts, framing choices
  (excluded options, accepted premises, question bundling). Give each its
  strongest realistic alternative, the cleanliness test, principle or
  correctness property that alternative fails, and evidence (`path:line`,
  probe, ruling id); scale from one line to a mini decision packet by stakes.
  Ask about any ruling you cannot ground.
- Repeat the list, with later rulings, in each release or ratification
  request.
- End every walkthrough and explanation with an offer to ask. Once the user
  accepts, ask under [Question format](#question-format): adopt the end state,
  then one question per contested choice, no cap per round.
- Derive process questions from the root fix. Step up an abstraction level
  when all options feel wrong.
